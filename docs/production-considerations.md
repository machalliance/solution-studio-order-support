# Production considerations

WISMO is a prototype. This page lists what a production implementation should look at first — starting with **model cost**, the largest running cost — and says, for each item, what would change and what would need testing. Nothing here is implemented unless it says so.

## 1. Model cost

### What was measured (sizes from a captured request; step and turn counts from the trace database; no real model calls)

| Fact | Value |
|---|---|
| Agent system prompt | \~40,200 characters (\~10k tokens) |
| Tool definitions | 15 tools, \~16,400 characters (\~4k tokens) |
| **Fixed prefix resent on every model step** | **\~14.5k tokens** |
| Model steps per chat turn | 2.7 on average (4,055 steps over 1,499 recorded turns) |
| Turns per conversation | median 3, mean 3.8, 90th percentile 8 (115 recorded conversations) |

The cost driver is the fixed prefix, not the conversation: it is resent on every step of every turn, so caching it (lever a) is the largest saving. The sizes above are what the agent actually sends to the model: the instructions plus one 210-character line the server adds, and the tool definitions as the provider receives them. The agent framework (Mastra) adds nothing of its own to the prompt.

A turn that ends in a card (the order list, the item picker, the two offer cards) takes one model call, with no extra step after the card (`stopWhen` in `server.ts`), so the step average above is slightly high.

### Estimated cost per conversation

Assumptions (estimates, roughly ±40%): Sonnet-4.5-class pricing of \$3 / \$15 per million input / output tokens, \~4 characters per token, \~300 output tokens per step. The "Without caching" column is the cost with prompt caching off; the "With prompt caching" column is how the app runs as shipped (one typical conversation measured at about \$0.14 — see lever a). Check current pricing before relying on it.

| Conversation | Model steps | Without caching | With prompt caching |
|---|---|---|---|
| Simple tracking question (median, 3 turns) | \~8 | \~\$0.40 | \~\$0.12 |
| Longer chat (90th percentile, 8 turns) | \~22 | \~\$1.10 | \~\$0.35 |
| Damage claim with a photo (\~7 turns) | \~20 | \~\$1.20 | \~\$0.40 |

A photo adds \~2,500 tokens (at the 1568px the widget shrinks it to), resent on every later step.

### Levers, in order of value

**a. Prompt caching — the largest, with no change in behavior.** *Status: built, and measured twice against the real provider.* The agent's instructions are a system message carrying the marker described below (`wismo-agent.ts`), and a test (`tests/mastra/prompt-caching.test.ts`) captures the requests of a multi-step turn and checks that the marker is on every call, the prompt text is the agent's own, and all 15 tools are still sent.

**Measured against the real provider** (one conversation of four turns, eight model calls, about \$0.20): the first call wrote 14,454 tokens (the tools and the prompt) to the cache, and every later call read exactly those 14,454 tokens back, 80% of all input tokens. At list prices that conversation cost about \$0.14 against \$0.40 uncached, a 66% saving, in line with the table below. The replies were ordinary and the agent's behavior did not change. The cache lasts about five minutes, so the first message after a quiet period pays the one-time write (1.25×) and a busy period pays it once per five minutes, not per customer.

**Measured in a live browser session** (a real Chrome, the storefront and the Escalation Desk, 20 model calls across two chats): exactly one cache write, the very first call; 84% of 325,285 input tokens were read from the cache; about \$0.29 against \$1.02 uncached, a 72% saving. The second chat, a fresh page load and so a new session and conversation, read the cache the first chat had written, so the cache is shared across conversations. Nothing customer-specific is in the cached part (see the requirements below).
- *How it is done:* the agent's `instructions` are a system message object carrying `providerOptions: { anthropic: { cacheControl: { type: "ephemeral" } } }` instead of a bare string. Mastra's `SystemMessage` type accepts this (checked against the installed type definitions and by the request-capture test). A marker on the system block caches the tools and system prompt together (Anthropic orders the prefix tools → system → messages). Optionally add a second marker on the latest message to cache conversation history within a turn.
- *Requirements:* the prefix must be identical on every step. The instructions are static text; the one customer-specific line the server adds (about 210 characters, `server.ts`) is a separate system block placed after the marker, so it does not break the cache. Keep anything that varies per customer or per request out of the instructions and the tool definitions, and put it in that block or in the messages. Editing the prompt or a tool definition changes the prefix, so the first conversation after a deploy pays one write. The prompt must exceed the model's minimum cacheable size (1,024 tokens; ours is \~14.5k). The default cache lifetime is 5 minutes; cache writes cost 1.25× the input price and reads 0.1×. The app changes `toolChoice` between steps (`prepareStep` in `server.ts`); per Anthropic's rules that invalidates cached *messages* but not the tools or system prompt.
- *What to test:*
  - Free (done: `tests/mastra/prompt-caching.test.ts`): a test against a fake Anthropic server (`ANTHROPIC_BASE_URL`) asserting the request carries `cache_control` on the system block, identically on every step of a turn.
  - Paid (done): several real calls within five minutes; confirm the later ones report cache-read input tokens and the replies are unchanged.
  - Behavior: caching does not change the prompt text, so the prompt-dependent behavior checks (fault attribution, escalation wording) need no re-run — unless the prompt is also edited.
- *How to see it working in production:* the observability store records usage on every model step (`mastra_ai_spans`, spans of type `model_step`; the attributes are stored as SQLite JSONB, so read them with `json(attributes)`): `usage.inputDetails.cacheRead` and `cacheWrite5m`. A healthy busy system shows a read on nearly every call after the first within each five-minute window; a run of calls with no reads means the prefix changed or traffic is too sparse for the cache to stay warm.
- *Provider:* the marker is written for Anthropic models (`providerOptions.anthropic`). A different provider needs its own setting, and changing `WISMO_CHAT_MODEL` is worth repeating the cheap check above (read the cache fields after a few calls).
- *Rollback:* remove the marker.

**b. Shrink the prompt.** The instructions are long (about 10k tokens). Trimming reduces every step's cost but *changes behavior* — the agent's reading of fault, in particular, is sensitive to its wording (see §2). Any trim must be re-measured with full scripted conversations, which costs real model calls.

**c. Fewer steps per turn.** The agent replies through a `respond_to_customer` tool call, so every reply costs a step of its own, on top of any lookups. Restructuring that is a behavior change with the same re-measurement cost as (b).

**d. Model tiering.** A cheaper model for low-risk turns (order tracking) and the stronger one for damage claims and escalations. The agent's fault and escalation judgments are model-dependent, so the cheaper model needs the same scripted measurement before it is trusted with them.

**e. Spend limits and monitoring.** Set a provider-side spending limit and alert before it is reached. The app already shows a customer-safe "I can't help with this right now" message, with no Try again button, when the provider reports a spending cap (`apps/agent/src/mastra/chat-errors.ts`). It does not track spend itself.

### Already done

Prompt caching on the agent's instructions and tools (lever a; measured at about two thirds off a typical conversation), `maxRetries: 4` on the chat agent (a failed model call is retried at 1, 2, 4 and 8 seconds), a "Still working on it…" notice after 12 seconds, a Try again button only when a retry can help, and browser-side shrinking of photos to 1568px.

## 2. Things a production implementation should know about the agent's judgments

- **Fault is the model's reading of the customer's words, never verified.** An own-fault damage claim from a non-VIP customer is denied automatically, so the wording that decides it matters: the instructions define the customer's own fault as something the customer *did*, and treat damage during ordinary use as not their fault. When the account is silent or could be read either way, the agent asks one open question, and if it is still unclear it leaves fault unstated, which the policy sends to a person (a wrong "own fault" would be a final automatic denial). Measure any prompt or model change against equivalent statements ("tore during normal wear" / "got a tear while wearing it") before shipping it.
- **The agent can say an offer twice.** The escalate-to-support and start-a-new-chat cards are meant to be the agent's whole reply, but the model occasionally also sends the same sentence as an ordinary reply, so it appears twice in one message. The storefront widget hides a card's sentence when a reply in the same message already says it (identical text, ignoring spacing and capitals); a reworded repeat would still show twice. The fix is in the widget, so a different chat client needs the same check, or a server-side one.
- **A photo's label is not trusted.** A pasted image is always named `image.png` and typed PNG by the browser whatever it holds; the app reads the type from the bytes (client and server).

## 3. The container image

Docker is optional: the app also runs directly with `npm`. The image (`Dockerfile`) and `docker-compose.yml` run the agent, the Escalation Desk and the storefront as three containers from one image, with the agent's data in one named volume. Things to know:

- **Contents.** The image carries the runtime dependencies of all three apps and contains no database, tickets file or tests. API keys are supplied at run time, and it runs as an unprivileged user.
- **The agent must stay a single process.** Case events are an in-process emitter and several settings are held in memory (see §4); do not scale the agent service beyond one container.
- **The browser talks to the agent directly**, using the page's own hostname plus the agent port, and that port is baked into the Desk and storefront at build time (`NEXT_PUBLIC_AGENT_PORT`). Behind a reverse proxy or on a different public port, set `NEXT_PUBLIC_AGENT_URL` and rebuild.
- **State lives in the `agent-data` volume** (database, policy versions, support-ticket record). The volume is filled from the image once; a newer image does not overwrite it. `docker compose down -v` deletes it.
- **Image-scan findings.** After applying the Debian security updates and refreshing npm, the findings that remain are the Debian packages with no fix from Debian (glibc, util-linux, zlib and similar) and the packages bundled inside the base image's own npm. Rebuild regularly to pick up patches, and rescan with Trivy (image mode) and Grype. Removing npm from the final image would clear the npm-bundled findings; it stays in because the services start through `npm run`.
- **No TLS, no authentication.** Both are out of scope for the prototype; terminate TLS in front of it and add authentication to the Desk before exposing it.
- **Licenses inside the image.** The production dependencies are MIT, Apache-2.0, ISC or BSD, with two exceptions the prototype accepts: the prebuilt libvips packages that `sharp` brings are LGPL-3.0-or-later (Next.js installs `sharp` as an optional dependency, and neither app's code uses `next/image`), and `caniuse-lite` is CC-BY-4.0. The Debian base image carries its own licenses too, some of them GPL. None of this affects the source repository. If you redistribute a built image, keep `NOTICE` (it lists the attribution each of these needs) and the packages' own license files with it, and honor the LGPL and Debian terms; the LGPL libraries are linked dynamically and not modified.

## 4. Other gaps a production implementation would close

These are deliberate prototype boundaries, not bugs:

- Support ticketing is a stub (`escalate-support-ticket.ts` logs and returns a fake id); customer notifications are a stubbed email adapter.
- Case events are an in-process emitter, so the app assumes exactly one running agent process. A message bus is needed beyond that.
- **The server holds each conversation, tied to a session id the browser chooses.** A chat is one row (`wismo_threads`, in the same database as the workflow runs) keyed by `conversationId` and bound to the `sessionId` that started it; a request for another session's conversation, or for a thread stored under a different customer, is refused. There is no login, so anyone who holds both ids can continue that chat; they are random per tab but not secret, and production should bind a thread to the authenticated customer. A thread is capped at 200 messages, has no expiry (only a demo reset clears them), and keeps every photo a customer sent inside its row, so production should store photos once outside the thread and expire old threads. The "Escalate to support" route reads the stored thread by `conversationId` without a session check, for the same reason. A rep's decision or question pushed to a chat is also written into the session's most recently used thread by the in-process case events, so it shares the single-process limit above. A notice that arrives while the agent is still answering is stored after the answer, the order the customer sees (the widget shows a pushed message only once the answer has finished). "Try again" keeps the completed tool results of the failed turn and drops only its reply; it retries the message the browser names, and sends that message as a new one if the server never stored it (a dropped connection). The widget does not offer Try again once a rep's question or decision has arrived after the failed message: the library would remove everything after the retried message, including the notice, so the customer answers with a new message instead and the failed message and the notice both stay in the conversation. A request that bypasses the widget and retries anyway drops a notice that came after the failed message, because the history must end on the customer's message or a tool result.
- **A case's transcript starts after the previous case's turn.** In a chat that opens a second case, the second case's transcript begins at the first customer message after the first case was created, so a follow-up on the first matter sent in between is included in the second case. A case that is still open also keeps following the conversation, so the first case holds the later lines. A real matter boundary would need the agent or a person to say where one matter ends. The boundary is held in memory, so an agent restart forgets it.
- **The prototype deliberately puts no limit on the size of a request, a photo or a conversation.** Apart from one running turn per session and a cap of 200 messages per conversation, nothing is limited. A request body of 100 MB is accepted. A photo of up to about 10 MB passes the check, although the model API refuses one above about 7 MB as a file (the widget shrinks every photo it can read to about 1 MB, so the widget's own customers never meet this). A conversation holding about 25 photos makes each turn take over five seconds, freezes the whole process for about a second and a half, and sends the model API a request near its own limit (about 32 MB), after which every later message in that chat fails. Production should limit what a photo and a conversation can hold, and not stop the chat: about 4 MB per photo (above a high-end phone's normal photo of 2 to 4 MB), about 5 photos per conversation with 4 per message (five photos of 4 MB are about 27 MB as text, just inside the model API's request limit), and a request cap as a backstop against padding: about 32 MB while the widget still resends the whole chat with every message (the server reads only the newest), or about 25 MB if the widget sends only the newest message. A refused photo should get a clear message and text should keep working, and the widget should apply the same limits when a photo is attached. **The one real trade-off:** once a chat has used its five photos, a rep's request for another photo cannot be answered in that chat. If that matters, send the model only the newest photos and keep all of them stored. Keeping photos outside the thread (task 3.4.1) removes the problem at its source.
- **The text cleaning removes whole categories of hidden characters, with two side effects.** It removes every control and format character (zero-width characters, direction marks and overrides, soft hyphens, annotation marks, and Unicode tag characters, which spell text a model can read but no person can see), variation selectors other than the two that choose an emoji's plain or picture form, and lone surrogates, and it turns line and paragraph separators into line breaks, so a customer or pasted text cannot carry an instruction a rep never sees. The same cleaning applies to the customer's words in a support ticket. The side effects: it also removes the zero-width non-joiner and joiner that some scripts need (the Persian half-space, some Indic conjuncts) and the joiner inside emoji sequences (a family emoji splits into its members). A deployment serving those languages should keep those two characters.
- **A turn still ends at once for a tool that does not exist, or when the model service fails.** A lookup that merely fails (a mistyped order number, an order that is not the customer's) is answered: the error goes back to the model as the tool's result and the next step must reply. But if the model calls a tool that does not exist, or the service fails, after the agent's opening line ("Let me check on that"), the customer is left with that line; a service failure also shows the error with Try again.
- **The chat widget offers no way out of a full conversation.** At the 200-message cap the customer is told to start a new chat, but there is no button for it (the header has only Close). Each further message is sent and refused, and only one refusal message shows on screen, so the later messages sit without a reply. Reloading works, but it starts a new session, so a customer with an open case stops receiving live updates in that tab (the email stub is the fallback). A button in the refusal that reuses the agent's new-chat mechanism would keep the live connection. The composer also does not stop a message at the server's limit of 4,000 characters: a longer message is refused whole, with the reason, and has to be shortened and sent again.
- **A reply that breaks off halfway is stored as it was shown,** so the model sees the partial text in later turns; "Try again" removes it.
- **A customer's own words are still untrusted input to the model.** What the server cleans is structure: only a customer message is accepted, only text and photos, a length cap, invisible and direction-changing characters removed, a typed countdown marker neutralised, a photo's type read from its bytes. It cannot remove an instruction written in plain English by the customer who really typed it; that stays covered by deciding money, ownership and policy in code, by the checks on the agent's replies, and by treating fault (§2) as the one judgment that is never verified.
- Runtime settings (response windows, queue priority threshold, the spending ceiling) are held in memory and reset on restart.
- Order and delivery data is trusted as given. The app does not validate it (for example, a delivery date in the future); that is the order system's job.
- Operators can author and activate policy but there is no sandbox for trying a policy against sample requests.
- Refund "completion" is never known — the app records that a refund was *approved*, not that money moved.
- A customer's damage photo is stored inside the case record itself, and more than once (a damage case with a photo measured 5–8 MB). The Escalation Desk's refreshes and the timeout sweep read every case each time, so the Desk gets slower as photo cases pile up: with six cases on a 4-CPU server, a decision click could wait up to about 2.5 seconds behind a sweep. Production should store each image once in object storage and keep only its address in the case.
- **The admin routes accept a request from any web page.** The Escalation Desk's POST routes (settings, demo reset, case decisions, policies) read a JSON body whatever its content type and check neither the origin nor a token, and the CORS check compares only the port, so a page open in the browser of the person running the app can send them a plain cross-site request (checked with curl; how far a browser blocks requests to local addresses varies). Production should require `application/json`, check the origin, and put real authentication in front of these routes.

## 5. Legal, privacy and compliance

This prototype is a starting point to build from. It has not been reviewed against any country's laws and nothing here is legal advice; each item below is a prompt to check the rules that apply where you operate.

- **Telling customers they are talking to an AI.** The chat panel's subtitle reads "AI Assistant", and the agent has no instruction on how to answer "am I talking to a bot?". Rules on disclosing AI use differ by place and are changing, so check what yours require (the wording, where it must appear, what the agent must say when asked) and adjust the label and the prompt.
- **Automatic decisions about customers.** The shipped policy declines some claims without a person (a customer's own fault, outside the return window). Consumer-protection and data-protection laws in some places give customers rights that a shop's own policy cannot remove, such as statutory guarantees, withdrawal rights and limits on solely automated decisions. The shipped policy is an example, not a legal position, so check it against your local law. A customer who disagrees with a decision is offered an escalation to support.
- **Customer data.** Names, emails, photos and conversations are stored with no expiry, and conversations and photos are sent to the model provider while a chat runs, so a privacy notice, data-processing terms and a retention and deletion process are needed. A photo of about 1 MB or less and no more than 1568 px on its longer side is sent as the customer's device made it, so any location or device details inside the file are kept, stored and shown to reps; re-encode photos or strip their metadata on the server.
- **Fonts load from Google's servers.** Both front ends request their fonts from Google Fonts, which sends each visitor's address to Google, and some places treat that as a disclosure of personal data. Self-host the font files instead (check each font's license).
- **Tracking and return-label lookups need no login, and their numbers are sequential.** `/tracking/TRK-<order number>` and `/returns/RTN-<order number>` (with `_<item codes>` added for part of an order) answer anyone who types a number, and the tracking answer includes the name of the person who signed for the order. Use unguessable tokens and leave the name out.
